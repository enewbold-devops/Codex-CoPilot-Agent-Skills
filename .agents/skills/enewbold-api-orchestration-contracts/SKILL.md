# API Orchestration and Handoff Contracts

Follow [AGENTS.md](../../../AGENTS.md), [profile selection](../../../docs/architecture/profiles/README.md), the selected profile, consuming solution record and accepted ADRs. The Solution Architect owns design; the MCP Platform Engineer consumes approved contracts. Use [registry guidance](references/registry-design.md), [review checklist](references/contract-review.md), and the [registry example](assets/example-registry.json). The example is synthetic, not a real API or a production contract.

## Workflow

1. Establish scope and evidence. Read the opportunity assessment, approved profile, intended users, allowed data and operations, source rights, constraints and approval state. For a new Tier 1 opportunity use enewbold-tier1-opportunity-assessment first. Separate verified, proposed, blocked and unverified claims. Do not silently approve a profile or vendor operation.
2. Inventory official API documentation/OpenAPI. Record publisher, documentation URL, version/date, operation ID, method, path template, parameters/location/schema, request/response schemas, pagination, limits, access, rights, provenance and errors. Resolve referenced schemas or mark unresolved. Exclude unsupported, undocumented, private or mutating operations for Tier 1, including side effects hidden behind GET; allow read-only POST only if documented and approved. Never use an arbitrary caller-provided URL. Do not execute live calls unless rights and approved scope permit them.
3. Map user intents/topics to semantic tools, not one tool per endpoint by default. Record operation IDs, purpose, input/output JSON Schema, contract version, provenance, no-result/error semantics, policy, execution budgets, optional resource/prompt/UI requirements. Keep vendor payloads behind adapter contracts; use current MCP documentation to determine supported protocol primitives. Use enewbold-mcp-tool-design for detailed individual tool review.
4. Define explicit handoffs with producer/consumer tool IDs and versions, JSON Pointers into validated schemas and instances, required fields, mapping cardinality, transform rules, preconditions, policy, error/no-result handling and execution ownership. Carry values explicitly between requests; never rely on server sessions, unchecked client context, retrieved instructions or unbounded chaining. No dynamic evaluation of mappings. Resolve each pointer, type/constraint compatibility and required-field coverage; use named, deterministic transforms with test cases when mapping is not identity. Mark incompatible or unresolved mappings BLOCKED.
5. Define runtime enforcement. Require native ESM JavaScript, JSDoc classes, runtime input/output validation and checked transformations; no TypeScript requirement. In Tier 1 enforce public read-only allowlists, fixed origins/paths, validated parameters, redirect/SSRF protection, bounded response/pagination/timeouts/retries, provenance, privacy and fail-closed behavior. Tier 2/3 additionally preserve trusted identity/tenant context, credentials, authorized writes, idempotency and durable state/recovery when applicable. Skills, prompts and MCP annotations guide selection, not enforcement.
6. Produce consuming-solution deliverables: docs/architecture/api-orchestration.md, contracts/api-orchestration-registry.json (validate against assets/registry.schema.json), versioned request/response JSON Schema artifacts or embedded schemas, and docs/architecture/contract-verification.md with the required test matrix. Use the repository's accepted locations if different. Do not store credentials or private sample payloads. Record official source links, retrieval date/version, assumptions and migration/compatibility decisions.
7. Verify registry structure and semantics. Validate with a JSON Schema 2020-12 compatible validator, check unique IDs, resolve all cross-references, schema/pointer compatibility, required consumer inputs, operation rights/side effects and execution budgets. Verify positive, negative, empty, pagination, upstream-failure and handoff cases with synthetic fixtures; do not claim runtime tests if no executable code exists. Use [review checklist](references/contract-review.md).
8. Return READY FOR IMPLEMENTATION only for approved bounded design with resolved required source/contract/security prerequisites; otherwise DESIGN BLOCKED with owners and next evidence. Deployment gates remain separate. Handoff the registry revision, schemas, constraints, evidence, gate status and tests to the Engineering Lead and MCP Platform Engineer. Obtain Principal Engineer approval for material contract or architecture decisions; route independent security and verification.

Use enewbold-third-party-saas-integration for implementation of approved provider adapters and enewbold-adr-authoring for significant contract or host decisions. Do not provision infrastructure or author production tool code during this skill.
