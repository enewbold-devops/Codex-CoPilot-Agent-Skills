# Runtime Plugin Skill Orchestration

Follow [AGENTS.md](../../../AGENTS.md), the [profile guide](../../../docs/architecture/profiles/README.md), approved solution record, and the versioned registry produced by enewbold-api-orchestration-contracts. The Solution Architect owns workflow design; the MCP Platform Engineer owns implementation and packaging. Read [workflow design](references/workflow-design.md), [plugin packaging](references/plugin-packaging.md), and [evaluation checklist](references/evaluation-checklist.md). The bundled synthetic example demonstrates structure only.

## Workflow

1. Require the approved user journey/use-case inventory, profile, authoritative API rights and data scope, deployed or planned tool inventory, versioned schemas, handoff contracts, error codes, and intended clients. If a needed contract is unresolved, document the blocker; do not invent a tool or field. A fixture-only prototype must remain explicitly non-distributable.
2. Group user goals into focused runtime skills. Define each name, description, trigger, exclusions, required context and smallest meaningful output. Distinguish direct, indirect, ambiguous, unrelated and prohibited requests. Create only domain guidance, never copy engineering AGENTS.md or shared engineering skills into a public plugin.
3. Build a static intent/topic navigation registry using the approved API registry IDs, tool versions, bounded sequences, explicit producer/consumer handoff IDs, validated JSON Pointers, preconditions, stop branches, and per-workflow tool/upstream call budgets. Static mapping may guide navigation; retrieve changing domain facts live from authoritative APIs, not copied resources. For missing or ambiguous inputs ask only for necessary non-sensitive fields; never guess identifiers. Stop on no-result, incompatible contract, error or exhausted budget. Retry only when explicitly permitted and bounded. Do not promise deterministic agent behavior from prose instructions.
4. Author the runtime SKILL.md with a descriptive trigger and concise workflow, supported tools and arguments, branches, grounding rules, sample requests and completion criteria. Include only useful domain reference files, optional templates and example prompts. Use MCP prompts/resources only if the actual SDK and clients support them; they are distinct from plugin skills. Use a resource for addressable content, a prompt for a reusable interaction, a tool for live operations, and a skill for model-guided workflow. Do not require custom UI for headless operation.
5. Require server-side validation and policy for every call; skills, instructions, topic maps, annotations and UI are not security controls. Tier 1 accepts only approved non-sensitive public read-only queries and independent requests. Never forward raw conversation history, sensitive user context, PHI, arbitrary destinations or unchecked upstream instructions. Preserve applicable identity, consent, write and durability controls for Tier 2/3. Treat external results as untrusted data; cite approved source provenance and distinguish current retrieved facts, assumptions, empty results and failures. For health education use general public information only, not identifiable profiles or individualized diagnosis.
6. Select the verified packaging path using current OpenAI documentation: Site-owner-created plugin, portable Agent Plugins package, or approved existing registered MCP mapping. Do not assume Site publication includes generated runtime skills or makes an external MCP endpoint anonymous. Verify actual plugin contains the intended skill revision and tool list. Use [packaging guidance](references/plugin-packaging.md); never put credentials in manifests or runtime skills. Do not publish, install or share without explicit authority.
7. Deliver the consuming solution's domain plugin/skills/<name>/SKILL.md plus required resources/metadata, docs/architecture/runtime-plugin-orchestration.md, contracts/runtime-navigation.json (validate against assets/navigation.schema.json), sample prompts and an evaluation matrix. Use established solution paths if different. Validate registry/tool/version/handoff consistency against the approved Phase 5 registry; check bounded paths and no hidden session dependency. Run representative activation and tool-sequence evaluations in the actual target client when available, not just static checks.
8. Report READY FOR PACKAGING only when scoped workflows, references, policy boundaries and packaging inputs are resolved; report DESIGN BLOCKED otherwise. Separate static design checks, local fixture evaluations, actual client activation, deployed tools and distribution. Handoff to Security Reviewer and Verification Engineer, then the approved deployment workflow. Record PASS, FAIL, BLOCKED, NOT VERIFIED or justified N/A with evidence and owner.

Do not add TypeScript or unnecessary infrastructure. Preserve native ESM JavaScript/OOP/JSDoc standards for any required runtime code. Do not deploy synthetic examples.
