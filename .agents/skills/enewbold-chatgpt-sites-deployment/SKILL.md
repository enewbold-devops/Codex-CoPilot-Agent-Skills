# ChatGPT Sites Deployment

Follow [AGENTS.md](../../../AGENTS.md), the [Tier 1 profile](../../../docs/architecture/profiles/tier-1-public-stateless-mcp.md), the approved solution record, API registry, runtime navigation registry (when used), implementation evidence and accepted ADRs. MCP Platform Engineer implements; Verification Engineer independently verifies; Security Reviewer reviews public trust boundaries; Engineering Lead coordinates approval. Read [runtime and import guide](references/runtime-and-import.md), [release runbook](references/release-runbook.md) and [deployment evidence template](references/deployment-evidence.md).

## Workflow

1. Confirm the actual scope, owner/workspace, target audience, release authority, intended Site/MCP/plugin access channels, approved origin/operations, data-use limits and costs. Obtain explicit approval for live deployment, public exposure, sharing, custom domain or public submission; a request to generate a scaffold/skill is not publication approval. Use restricted or offline fixtures until mandatory prerequisites are satisfied. Never create or expose an unauthorized endpoint.
2. Refresh official documentation. Record dated evidence of account/role entitlements, supported creation/import path, template, local build tooling, host runtime, JavaScript compatibility, dependency versions, SDK/protocol era, supported headers/streaming, outbound HTTPS, secrets and request/concurrency/size/time/quota limits. Check actual constraints in the authorized environment. Docs are not account entitlement or runtime proof.
3. Create or inspect the smallest supported Sites project. Prefer a verified official template/import or Site-owned edit flow; adapt the Phase 6 portable native ESM JavaScript/OOP/JSDoc core to the actual host. No TypeScript/TSX source or compilation requirement, Node-only listener assumption, database, tenant auth, tunnel or background worker by default. Check template output and package scripts; if JS-only compatibility is unavailable or unknown, block and propose an approved alternative stateless host ADR instead of bypassing constraints.
4. Implement a verified SDK transport using its version-specific APIs. Keep Node development and Web-standard host adapters separate. Register only approved semantic tools with runtime schemas and accurate annotations. Validate Host and any present Origin using SDK/adapter or verified ingress controls; do not assume bare fetch handlers do so. Verify finite request body, response, timeout, cancellation, egress, concurrency and rate/cost controls, safe error mapping and request independence. Use actual host limits or approved external operational controls; no durable business/user/session state. Require the public MCP security review before any public exposure.
5. Pin supported versions, install from lockfile, run JavaScript unit/contract/negative tests and actual local SDK protocol tests (modern per-request and legacy initialize flows as applicable). Use MCP Inspector or equivalent compatible client; record exact versions, tool list, input/output, valid/invalid calls and concurrency. Test no hidden session dependence. No uncontrolled live data or production credentials. Fixture tests alone do not prove wire protocol.
6. Use only the documented authorized Sites build/import/publish mechanism. Record source revision, manifest, build output/hash, Site ID/URL, runtime configuration, secrets presence (not values), environment, owner and deploy revision. Stage with synthetic data and restrictive access if supported; verify real hosted MCP execution and approved live public API read only after rights and security prerequisites pass. If the supported flow cannot stage safely or evidence cannot be obtained, stop with BLOCKED/NOT VERIFIED.
7. Verify independently: Site access as intended visitor; actual Sites MCP execution; anonymous external MCP endpoint only if required, using an independent client with no ChatGPT/session credentials; installed plugin access, connection, exact skills/tools and workflow for intended users; public directory submission/review only if explicitly required and authorized. Public Site publication does not establish the other outcomes. Do not bypass access restrictions or reuse personal authentication to prove anonymity.
8. Review release evidence with Security Reviewer and Verification Engineer. Use PASS, FAIL, BLOCKED, NOT VERIFIED or justified N/A per subcheck; every applicable mandatory gate must PASS before release. Keep development and production configuration separate. Define tested rollback/disable access, incident owner, privacy-safe alerts, quota/cost stop conditions, version compatibility and update verification. Do not call platform controls effective without actual evidence.

Deliver docs/architecture/deployment.md and docs/verification/sites-release-evidence.md (or accepted project paths), the pinned JS-compatible package/adapter changes, test evidence, security findings and release/rollback plan. Label documentation-only, local, hosted and distribution evidence separately. Do not publish without explicit authority.
