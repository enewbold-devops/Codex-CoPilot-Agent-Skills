# Tier 1 Opportunity Assessment

Follow [AGENTS.md](../../../AGENTS.md), [profile selection](../../../docs/architecture/profiles/README.md) and [Tier 1](../../../docs/architecture/profiles/tier-1-public-stateless-mcp.md). The Engineering Lead owns the assessment; the Solution Architect validates technical feasibility. Use the [assessment template](references/opportunity-assessment-template.md) and [qualification rules](references/qualification-rules.md). This is an engineering-time discovery skill, not a runtime plugin skill or release authorization.

## Workflow

1. Establish the opportunity envelope: organization, products/services, intended audience, stakeholder journey, actual challenge, desired outcome, constraints and exclusions. Distinguish documented problems from hypotheses. For missing details that do not prevent discovery, record assumptions; do not fabricate stakeholder feedback.
2. Identify customer engagement friction: time, risk, navigation, information fragmentation, accessibility and relevant regulatory/compliance pressures. Propose measurable baseline and outcome metrics, labeled estimates when not measured. Identify who benefits and what existing workflow changes.
3. Discover authoritative sources and official API documentation. Record publisher, URL, version/date, operation IDs, methods/paths, schemas, pagination, quotas, access mechanism, terms/licensing, redistribution, attribution, data classification and source freshness. Separate documented facts, assumptions and unresolved evidence. Never invent endpoints or interpret public availability as permission to reuse. Do not send sensitive data, test writes, bypass access controls or perform unauthorized probes.
4. Screen solution scope: allowlisted public non-sensitive read-only operations, validated non-sensitive queries, no user/tenant OAuth, no private records, business writes or durable business/session state. Scoped provider key for public reads only if permitted and protected. Escalate protected data/writes/identity to Tier 2 candidate; durable workflows to Tier 3 candidate. A Sites runtime limitation alone warrants a host decision, not automatic Tier 2.
5. Propose a minimal agentic experience: semantic tool names, intent/topic mapping, source operation mapping, preliminary input/output fields, explicit follow-up handoff values, optional resources/prompts and optional UI justified by value. Do not design arbitrary URL tools. Keep public policy enforceable server-side; runtime skills are guidance. Avoid indexing/replication when live public APIs satisfy the need.
6. Assess feasibility: native ESM JavaScript, OOP/JSDoc, runtime schemas, host adapter and actual SDK/runtime constraints; no TypeScript source/compilation. Check current official Sites/OpenAI/MCP documentation via available authoritative tools. Distinguish documented compatibility, actual Sites execution, public Site access, anonymous external MCP (if required), and plugin installation/distribution. Record quota/cost assumptions, safety controls and unknowns. Do not provision infrastructure or claim tested deployment.
7. Complete all ten mandatory gates using the qualification rules. Record PASS, FAIL, BLOCKED, NOT VERIFIED or justified N/A for subchecks; mandatory gates require evidence, not weighted averages. Assign an owner and next evidence action to each unresolved gate. Report the optional prioritization score separately from eligibility.
8. Deliver the opportunity brief and proposed scope using the template. Recommend one decision: PROCEED TO DESIGN (requirements fit with no disqualifying gate and explicit evidence plan; not release-ready), BOUNDED PROTOTYPE (only safe unresolved technical questions), DISCOVERY BLOCKED, REDESIGN/RECLASSIFY, or REJECT. Escalate material decisions to the Principal Engineer. Require applicable mandatory gates PASS before release.
9. Handoff to Engineering Lead and Solution Architect with the profile record, evidence, proposed contracts, limitations, gates and acceptance criteria. Use `enewbold-architecture-impact-analysis` and `enewbold-mcp-tool-design` for subsequent design, and `enewbold-third-party-saas-integration` only after scoped approval. Route public security review and independent verification. Do not invoke nonexistent future skills.

## Evidence discipline

Use official current sources for product capability, API contracts, licensing and regulation. Cite dated links and distinguish legal/compliance questions requiring qualified review. No production credentials, sensitive inputs, uncontrolled API calls, unsupported hosting promises, invented stakeholder findings or approval inferred from a score. If documentation is inaccessible, record the blocker and safe next action. An opportunity may be worth pursuing before deployment evidence exists; never label it release-ready.
