# Native JavaScript OOP Scaffolding

Follow [AGENTS.md](../../../AGENTS.md), [profile selection](../../../docs/architecture/profiles/README.md), the consuming solution record and accepted ADRs. The MCP Platform Engineer owns implementation. The Solution Architect owns contract and boundary decisions; Security Reviewer and Verification Engineer remain independent. Read [scaffold conventions](references/scaffold-plan.md), [runtime adapters](references/runtime-adapters.md) and the [reference core README](assets/reference-core/README.md) as needed.

## Inputs and prerequisites

Require the approved profile, bounded implementation scope, authoritative API evidence, operation/tool/handoff registry from enewbold-api-orchestration-contracts, versioned schemas, policy limits, expected host/client, acceptance criteria and unresolved gates. If a required design decision is unresolved, stop that implementation portion or create only an explicitly approved offline fixture prototype. Never infer endpoints, credentials, client support or deployment capability from an example.

## Workflow

1. Inspect the consuming repository and existing conventions. Preserve unrelated files and accepted decisions; do not overwrite working scaffolds. Identify local Node.js and actual deployment runtime constraints. Select Tier 1 by preference only when requirements qualify; do not introduce Azure, SQL, Dataverse, tenant auth, durable state or UI by default.
2. Generate the smallest coherent native ESM JavaScript solution: package.json type module, explicit import/export, focused classes, meaningful JSDoc, constructor injection, runtime schemas, composition root, semantic tools and separated core/service/policy/adapter boundaries. Use pure functions for stateless transformations and required host entrypoints. No TypeScript/TSX source, TS configuration or TypeScript compilation requirement. Executable JavaScript dependencies authored in TypeScript are permissible.
3. Use the bundled reference-core asset as an offline teaching baseline, not as a production server or actual provider implementation. Copy only relevant files; replace synthetic tool IDs, schemas, operation mappings, limits and provenance with approved contracts. Use a JS-compatible runtime validator for full production schemas (for example a verified JSON Schema implementation or supported SDK schemas); the reference uses explicit validators for one small contract. Ensure discovery metadata and runtime enforcement agree, validate both input/output, and test handoffs against actual schemas. Do not execute arbitrary registry expressions.
4. Implement the approved API adapter with fixed origins/methods/paths, validated parameters, response/schema limits, cancellation, bounded pagination/retries, no redirect forwarding, safe error normalization, provenance and untrusted upstream data handling. Tier 1 must remain read-only, independently executable and free of durable business/user/tenant/session state. Make provider calls injectable for testing. Enforce actual host request/rate/cost/abuse limits; do not rely on a per-process counter for a scaled public service. Preserve all applicable protected-operation and durable controls in Tier 2/3.
5. Implement actual MCP transport using a supported, verified SDK and exact version. Do not handwrite JSON-RPC/Streamable HTTP or assume historical initialize behavior is the only protocol. Verify modern and legacy behavior as required by intended clients; create request-scoped SDK server instances for stateless paths. Use the host adapter guide to select the runtime. Separate Node-only HTTP entrypoint from Web-standard request handler, and select the actual Sites project template/import mechanism from current official docs. Pin dependencies, install and generate the lockfile using available package tooling. Do not invent a Sites entrypoint or use a stub as a protocol implementation.
6. Add JavaScript unit, adapter, contract, negative/security and concurrency tests; add actual protocol/client tests for the chosen SDK and runtime. Use fixtures/sandbox instead of unauthorized live API calls. Run the appropriate npm scripts; report actual output and blockers. For Tier 1 verify independent requests, operation allowlists, malformed inputs, output validation, upstream failures, timeout and response bounds, redaction and approved public behavior. Verify deployed Sites execution, public Site access, anonymous external MCP access and plugin distribution separately when required.
7. Deliver application modules, versioned contracts, tests, package/lockfile as applicable, README, environment variable examples without secrets, architecture/profile and verification documentation. Keep engineering-time skills separate from runtime plugin guidance. Document any optional UI and support requirements. Return implementation status and unresolved gates; do not label fixture-only scaffold production-ready.
8. Route independent security and verification; use enewbold-code-change-verification and the selected profile. Use enewbold-third-party-saas-integration for provider adapters and enewbold-apps-sdk-tool-ui only when UI is approved. Escalate changes to contracts, identity, persistence or hosting via the Engineering Lead and Architect.

Do not add speculative base classes, hidden state, arbitrary HTTP tools, production secrets, hardcoded real vendor operations or a mandatory dependency merely because a previous solution used it.
